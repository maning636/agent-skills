# KPI 仪表盘 (kpi-dashboard)

## 1. 适用边界

### 1.1 适用场景
- 业务复盘需要 KPI 可视化（周报/月报）
- 新团队/新业务线建立数据基础
- 监控关键业务指标（转化/留存/活跃）
- 高管需要一个「一眼看懂业务」的入口

### 1.2 不适用
- 单点指标分析（属 `data-analysis` skill）
- 数据仓库建模（属 `data-engineering` skill）
- 实时大屏（> 1s 刷新频率，属 `real-time-monitoring` skill）

## 2. 指标体系设计（O-M-A-R）

### 2.1 四层指标树

```
O - Objective (目标层)         北极星指标 + 战略目标
  ↓
M - Measure (结果层)         业务结果指标（收入/用户数/转化率）
  ↓
A - Action (行动层)          团队/产品可影响的指标（DAU/转化率/留存）
  ↓
R - Result (反馈层)          实时业务状态（在线人数/销售额/异常）
```

### 2.2 北极星指标选择（NSM）

**好 NSM 的标准**：
- 反映用户从产品中获得的核心价值
- 是领先指标（领先于收入）
- 可被团队直接影响
- 简单到 1 句话能解释

**典型 NSM**：
- Airbnb：订房晚数
- Facebook：日活用户（DAU）
- Uber：每周完成订单数
- Slack：日活发送消息 ≥ 2 条的用户数
- Notion：每周创建文档 ≥ 1 个的用户数

### 2.3 指标分层（北 → 南）

| 层级 | 指标类型 | 更新频率 | 责任人 |
|------|---------|---------|--------|
| L1 北极星 | 业务核心 | 日/周 | CEO/业务总 |
| L2 一级指标 | 业务结果（收入/用户/转化）| 日 | 各业务线 |
| L3 二级指标 | 细分维度（按渠道/区域/产品）| 日 | 各 squad |
| L4 操作指标 | 实时状态（在线/活动/异常）| 小时/分钟 | 运营/客服 |

**金字塔原则**：L4 → L3 → L2 → L1，越往上越少（每层 3-7 个）

## 3. 仪表盘选型

### 3.1 选型矩阵

| 场景 | 推荐工具 | 优势 | 劣势 |
|------|---------|------|------|
| 中小企业起步 | Metabase / Redash | 免费、上手快 | 性能有限 |
| 中型企业 | Superset / Looker | 灵活、可控 | 学习曲线 |
| 大型企业 | Tableau / Power BI | 强大、企业级 | 贵 |
| 极简/个人 | Notebook + Plotly | 灵活、可编程 | 非交互 |
| 实时大屏 | Grafana + InfluxDB | 时序数据强 | 业务指标弱 |

### 3.2 选型决策树

```
Q1: 数据量 > 100GB？
  ├─ 是 → 考虑 Apache Superset + ClickHouse / Druid
  └─ 否 → Q2
Q2: 需要实时刷新？
  ├─ 是（< 1min） → Grafana + 时序 DB
  └─ 否 → Q3
Q3: 预算？
  ├─ $0 → Metabase / Redash
  ├─ < $5k/y → Superset 自部署
  └─ > $20k/y → Tableau / Looker
```

## 4. 仪表盘设计原则

### 4.1 5 秒原则
打开仪表盘 5 秒内应能识别：
1. 业务是好是坏（绿/黄/红状态）
2. 哪个指标异常
3. 最近 24h 的趋势

### 4.2 F 型视觉布局
```
┌─────────────────────────────┐
│   [北极星 + 状态]            │  ← 顶部：核心指标
├──────────┬──────────────────┤
│ [一级]    │   [趋势图]        │  ← 中部：结果 + 趋势
├──────────┼──────────────────┤
│ [细分维度] │   [异常告警]      │  ← 底部：细分 + 告警
└──────────┴──────────────────┘
```

### 4.3 图表选择

| 数据关系 | 推荐图表 | 备注 |
|---------|---------|------|
| 时间趋势 | 折线图 | 必含对比基线 |
| 占比 | 饼图（≤ 5 块）/ 树图（> 5 块）| 不超过 7 个分类 |
| 对比 | 条形图（横向）| 标签可读 |
| 相关性 | 散点图 | 标注 r 值 |
| 地理 | 地图 | 数据需有 geo 字段 |
| 漏斗 | 漏斗图 | 标注转化率 |

## 5. 数据源对接

### 5.1 常见数据源类型

```
- 业务 DB（PostgreSQL / MySQL / MongoDB）
- 业务 API（REST / GraphQL）
- 事件流（Kafka / Kinesis）
- SaaS（Stripe / Mixpanel / GA4 / HubSpot）
- 文件（CSV / Parquet）
- BI 工具（自带连接器）
```

### 5.2 数据建模（最小模型）

```
raw_events → dim_tables → fact_tables → aggregated_metrics → dashboard
   ↑           ↑            ↑                ↑
 原始事件     维度表        事实表           聚合指标
```

**原则**：
- raw_events 永远保留（可重算）
- 聚合结果可以丢（重算成本低）
- 时间分区（按 createdAt）

## 6. 异常告警设计

### 6.1 告警分级

| 级别 | 阈值 | 响应 |
|------|------|------|
| P0 | 业务完全中断（NSM 跌 0） | 5min 内首响 |
| P1 | NSM 跌 > 30% | 1h 内首响 |
| P2 | NSM 跌 10-30% | 当日处理 |
| P3 | 异常波动（无明确阈值）| 关注 |

### 6.2 告警去噪

- 不要每个指标都告警（噪音淹没信号）
- 同一根因的多个指标合并告警
- 用「事件」而非「指标」做告警（用户流失事件 vs DAU 指标）
- 周同期/日同期对比，避免节假日噪音

## 8. 反模式

- ❌ 没有北极星，只有几十个指标
- ❌ 指标没有责任人（孤儿指标）
- ❌ 实时数据源不够实时就承诺实时刷新
- ❌ 告警太多（值班疲劳）
- ❌ 仪表盘只给高管看（执行层看不到自己影响什么）
- ❌ 指标定义不清（DAU 是新 DAU 还是所有 DAU？）
