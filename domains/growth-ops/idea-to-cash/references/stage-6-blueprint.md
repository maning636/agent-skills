# 第 6 关 · 系统蓝图

> 原理见《Vibe Coding》系列第 6 章 ｜ 产物: `.vibe/blueprint.md` ｜ 过关: `gate.mjs check 6`
> 注意时序：此时第一版已经在跑（第 4 关）。这一关是**给它一个正式结构**，防止继续加功能时塌掉——不是从零画图。

## 陪跑流程

1. 用 ① 基于「VDF + 已跑通的第一版」出蓝图，**列出现状与蓝图的差距**（哪里要重构）。
2. 用 ② 把对接契约钉死（返工率最高的就是单位和格式）。
3. 蓝图你自己读一遍再放行——它是全项目最便宜的纠错点。落 blueprint.md → `gate check 6`。
4. 之后加功能，用 ③ 一次只动一个模块。
5. **fast 判据**：单功能点小工具可在模块段写「单功能点，豁免拆分」跳过拆分，但契约段必填。

## Prompt ① 出蓝图（基于现状重整，不是推倒）

```
你是资深架构师。需求：<<注入 .vibe/vdf.md>>
现状：第一版已本地跑通（工具与坑见下）：<<注入 .vibe/build-log.md>>
在蓝图确认之前不要动代码。输出四段，直接按 .vibe/blueprint.md 模板结构：
1. 模块拆分：3-7 个，各一句话职责 + 输入 + 输出
2. 数据流：谁把什么传给谁、什么格式
3. 对接契约：模块间数据的字段名/类型/单位/格式全部钉死（放代码块）
4. 与第一版的差距：现状哪些地方要重构才能对齐蓝图
原则：最小复杂度实现当前版本，不为"以后可能"过度设计；有技术风险直接点出。
```

## Prompt ② 契约钉死

```
基于蓝图：<<注入 .vibe/blueprint.md>>
把所有模块间传递的数据写成精确类型定义（我用 [TypeScript / Python dataclass / Go struct]）。
每个字段标：名字、类型、单位、格式、取值范围。
特别盯死容易各写各的：金额单位（元还是分）、日期格式、ID 类型、可空字段。
更新回 blueprint.md 的「对接契约」段。
```

## Prompt ③ 按蓝图分模块改造

```
基于蓝图与契约：<<注入 .vibe/blueprint.md>>
现在只动 [模块名] 这一个模块。要求：严格遵循契约字段名和单位；
先给实现计划我点头再动手；不要改其他模块、不要擅自改契约——
觉得契约要改就先停下来告诉我原因。
```

## 过关前自查

- 删掉任一模块，其他模块还能跑吗？（模块独立性口试）
- 契约里金额写单位了吗？日期定格式了吗？
