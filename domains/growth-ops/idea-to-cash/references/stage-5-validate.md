# 第 5 关 · 最小验证

> 原理见《Vibe Coding》系列第 5 章 ｜ 产物: `.vibe/validation.md` ｜ 过关: `gate.mjs check 5`

## 陪跑流程

1. 先用 ① 锁定"这产品到底被雇来干什么"（JTBD），确认第一版只做那一件事。
2. 用 ② 把功能清单砍出「V1 不做清单」。
3. **真的去验证**：落地页测试或假门测试（用 ③ 出验证页文案），发到 Q4 侦察出的渠道，把真实数字记进 validation.md → `gate check 5`。gate 会查「数据」段有没有数字——没数字 = 没真做。
4. 收到第一批反馈后用 ④ 整理、定 V2。

## Prompt ① JTBD 锁 MVP

```
产品与人群：<<注入 .vibe/direction.md 的「具体的人」「切换理由」段>>
先别给功能列表。用 Jobs to Be Done 分析：
1. 可能服务的具体场景 2. 每个场景里用户真正想完成的核心 job
3. 现有替代方案（含土办法）4. 哪个 job 最适合做 MVP 起点、为什么
5. 把推荐的 job 写成一句清晰的 JTBD 句子
```

## Prompt ② MoSCoW + ICE 砍功能

```
这是我想做的功能清单：[一条条列出来]
产品定位：<<注入 .vibe/vdf.md 的 V 段>>
1. MoSCoW 分四档：Must（MVP 必须）/ Should / Could / Won't（明确不做）
2. Must 和 Should 逐个打 ICE 分（影响力/信心/容易度各 1-10，相乘排序）
3. 单独输出「V1 不做清单」（所有 Could + Won't）——我要贴在显眼处
```

## Prompt ③ 验证页文案（验证用，不是卖货页——卖货页在第 14 关）

```
给这个产品写一个"验证落地页"：<<注入 .vibe/vdf.md 的 V 段>>
只要三行：一句话说清帮谁解决什么（3 秒看懂）+ 一句具体好处 + 一个"我想试"按钮文案。
再给我一句发群里的引导语，像真人分享，不像广告。
```

## Prompt ④ 反馈整理 → V2 优先级

```
第一批用户反馈原话：[一条条粘进来]
别急着给功能建议：先按出现频率归类诉求，标出反复出现的痛点和情绪词，
排优先级，告诉我下一版最该先动哪一个、为什么。
（成交后的"为什么买"复盘是第 16 关的事，别混在这里。）
```

## 过关前自查

- 数据是真实发生的吗？（发到哪、多少人看、多少人点——都要有数）
- 愿意点 ≠ 愿意付钱：有没有顺手问出付费意愿？
