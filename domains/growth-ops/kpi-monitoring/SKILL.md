# KPI 监控 (kpi-monitoring)

## 1. 适用边界

### 1.1 适用场景
- 业务上线后的连续性监控
- SLA（Service Level Agreement）履行
- 生产事故的快速响应
- 异常波动的早期预警
- 业务连续性保障

### 1.2 不适用
- 单次深度数据分析（属 `data-analysis` skill）
- 战略层 KPI 设计（属 `kpi-dashboard` skill）
- 实时交易监控（< 1s 刷新，属 `real-time-monitoring` skill）

## 2. 监控层次（4 级）

### 2.1 用户感知层（最终用户体验）

```
可用性：服务可用率（uptime %）
  - 月度 SLA：99.9% = 月度允许停机 43 分钟

性能：响应时间
  - P50（中位数）
  - P95（95 分位）
  - P99（99 分位）

错误率：4xx / 5xx 占比
  - 4xx 客户端问题
  - 5xx 服务端问题
```

### 2.2 业务结果层（业务指标）

```
核心 KPI：
  - 转化率（注册→付费、试用→付费）
  - 留存（7 日 / 30 日 / 90 日）
  - 活跃度（DAU / WAU / MAU）

收入 KPI：
  - MRR（月经常性收入）
  - ARR（年经常性收入）
  - ARPU（每用户平均收入）
  - Churn Rate（流失率）
```

### 2.3 应用健康层（系统状态）

```
应用层：
  - 应用进程存活
  - 应用响应时间
  - 应用错误日志

服务层：
  - 服务可用性
  - 服务依赖（DB / Cache / Queue）
  - 队列积压

中间件：
  - DB 连接池
  - Redis 内存
  - 消息队列长度
```

### 2.4 基础设施层（硬件 / 网络）

```
服务器：
  - CPU 使用率
  - 内存使用率
  - 磁盘 I/O
  - 网络带宽

容器（如果用）：
  - Pod 状态
  - 资源使用
  - 重启次数

云资源：
  - 负载均衡
  - CDN 命中率
  - 对象存储
```

## 3. 指标设计（S-M-A-R-T）

### 3.1 SMART 原则

```
S - Specific  指标定义具体（不是"性能好"而是"P95 < 500ms"）
M - Measurable 可量化（带数字 + 单位）
A - Achievable 可达成（不是 99.999% 而是 99.9%）
R - Relevant 相关性（与业务目标相关）
T - Time-bound 时间范围（"月度"不是"持续"）
```

### 3.2 指标要素

每个指标必须明确：
```
- 名称：清晰易懂
- 定义：怎么算
- 单位：%、ms、count、$ 等
- 数据源：从哪里采集
- 计算频率：实时 / 分钟 / 小时 / 天
- 责任人：谁来关注
- 当前值 + 目标值
```

### 3.3 反指标（Anti-Metrics）

仅看正向指标会被优化扭曲。例如：
- "客户数"↑ 可能因为拉低质量
- "转化率"↑ 可能因为放弃了低价值客户
- "DAU"↑ 可能因为活动拉新但无留存

**配套反指标**：
```
客户数 ↑ ↔ 客户质量评分
转化率 ↑ ↔ 客单价 ↓
DAU ↑ ↔ 7 日留存
```

## 4. 阈值设定

### 4.1 阈值类型

```
绝对阈值：固定值（如 CPU > 90%）
相对阈值：相对基线（如比上周同期低 30%）
统计阈值：基于分布（如 > 3σ）
智能阈值：基于历史模式（动态调整）
```

### 4.2 阈值设定方法

#### 历史数据法
```
取过去 30 / 90 天数据
计算 P95 / P99 / 中位数 ± 3σ
设定阈值为 P95 / P99
```

#### 业务影响法
```
从业务影响反推：
- 业务能容忍的最差情况是什么？
- 例：核心 API P95 > 1s，转化率掉 10%
- 阈值：P95 < 500ms
```

#### 对标法
```
对标行业：
- 业内 SaaS SLA 99.9% → 我们也 99.9%
- 业内 P95 < 300ms → 我们 < 500ms（追赶）
```

### 4.3 动态阈值（避免告警疲劳）

```
工作日 vs 周末：不同阈值
白天 vs 夜间：不同阈值
促销期 vs 日常：放宽阈值
```

## 5. 告警分级

### 5.1 P0 - 紧急（业务中断）

```
触发条件：
- 服务完全不可用
- 核心功能故障（如支付失败）
- 数据丢失风险
- 安全事件

响应：
- 5 分钟内首响
- 全员通知
- 24h 跟进
```

### 5.2 P1 - 高（核心功能受损）

```
触发条件：
- 核心功能性能下降
- 错误率上升
- 部分用户受影响

响应：
- 30 分钟内首响
- 值班 + 主管通知
- 4h 跟进
```

### 5.3 P2 - 中（非核心功能异常）

```
触发条件：
- 非核心功能故障
- 轻微性能下降
- 边缘用户群受影响

响应：
- 4 小时内首响
- 值班通知
- 24h 跟进
```

### 5.4 P3 - 低（关注类）

```
触发条件：
- 异常波动但未到阈值
- 潜在风险信号

响应：
- 工作时间处理
- 邮件通知
- 1 周跟进
```

## 6. 告警去噪

### 6.1 噪音来源

```
阈值过严：太敏感
告警风暴：同一故障多个指标同时告警
信息冗余：告警内容不清晰
误报：实际正常但触发告警
```

### 6.2 去噪策略

```
1. 同根因合并：同一故障的多个告警合并为一个事件
2. 静默期：同一指标 30 分钟内不重复告警
3. 升级降级：未响应 P1 自动升级到 P0
4. 抑制规则：维护期暂停告警
5. 智能去噪：基于 ML 的告警聚类
```

### 6.3 告警疲劳指标

```
- 每日告警数 > 50 → 告警疲劳
- 有效告警率 < 20% → 阈值过严
- 误报率 > 30% → 阈值需调
- 同一告警 > 3 次未处理 → 流程问题
```

## 7. 值班响应流程

### 7.1 标准 SOP

```
T+0：告警触发
  ↓
T+5min：值班首响（确认告警）
  ↓
T+10min：初步定位（影响范围 + 严重程度）
  ↓
T+15min：升级决策
  - P0/P1 → 通知主管 + 召集应急
  - P2/P3 → 记录到工单
  ↓
T+30min：开始修复
  ↓
T+1h：进展通报（每 30 分钟）
  ↓
恢复后：RCA（24h 内）
  ↓
1 周内：改进措施落地
```

### 7.2 值班交接

```
每日交接：
  - 当前告警状态
  - 进行中的事故
  - 已知问题
  - 风险预警
  - 文档更新
```

## 8. 根因分析（RCA）

### 8.1 RCA 方法

```
5-Why（5 个为什么）：
  问题 → 为什么 → 为什么 → ... 直到根因

鱼骨图（Ishikawa）：
  6M 维度：人 / 机 / 料 / 法 / 环 / 测

故障树分析（FTA）：
  自顶向下分解到根因
```

### 8.2 RCA 报告要素

```
- 事故概述（什么 + 何时 + 持续 + 影响）
- 时间线（关键节点）
- 直接原因
- 根本原因（5-Why 后）
- 短期修复（应急）
- 长期改进（预防）
- 责任人 + 时间表
```

## 9. SLA 管理

### 9.1 SLA 类型

```
可用性 SLA：99.9% / 99.99%
性能 SLA：P95 < 500ms
响应 SLA：首次响应 < 1h
恢复 SLA：P0 < 1h, P1 < 4h
支持 SLA：工单首响 < 24h
```

### 9.2 SLA 计算

```
月度可用性 = (月度总分钟 - 停机分钟) / 月度总分钟

例：月度 43200 分钟，停机 30 分钟
   可用性 = (43200 - 30) / 43200 = 99.93%
```

### 9.3 SLA 违约赔偿

```
阶梯式：
- 99.0% - 99.9%：服务费 10% 折扣
- 95.0% - 99.0%：服务费 25% 折扣
- < 95.0%：服务费 50% 折扣

注意 SLA 不计入：
- 客户原因停机
- 第三方服务故障
- 不可抗力
- 计划维护
```

## 11. 反模式

- ❌ 监控指标太多（噪音淹没信号）
- ❌ 阈值拍脑袋（无数据支撑）
- ❌ 告警分级不清晰（P0/P1 混用）
- ❌ 值班无 SOP（响应混乱）
- ❌ RCA 流于形式（找到直接原因就停）
- ❌ SLA 承诺过高（无法达成）
- ❌ 不做去噪（告警疲劳）
- ❌ 无反指标（指标被优化扭曲）
