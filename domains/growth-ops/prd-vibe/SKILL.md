## Purpose

`prd-vibe` 是专为 **OPC创业者、独立开发者、一人公司** 设计的PRD（产品需求文档）工作流。

传统PRD（如 `prd-development`）是为组织内跨职能团队设计的——需要写Executive Summary给老板看、需要TAM/SAM/SOM市场分析、需要多方利益相关者审批。这些对一个人创业的你，大多是**自己跟自己汇报的形式主义**。

但纯工具流（如 `write-prd`）又容易跳过**"为什么要做"**的战略思考，导致你做了一个技术很酷但没人用的产品。

**`prd-vibe` 取两者精华**：
- 保留**产品经理的问题结构化思维**（用户、痛点、成功指标）
- 保留**vibe coding所需的工程精确度**（页面、状态、字段、异常）
- 去除**组织协作的冗余环节**（战略上下文、多方对齐、审批流程）
- 强化**个人开发最需要的纪律**（强制范围冻结、六大盲区自检）

## 核心哲学：OPC的PRD不是为了"对齐团队"，而是为了"对齐自己"

一个人开发时，最大的敌人不是技术难题，而是：
1. **想法太模糊**——做到一半发现"原来我要的不是这个"
2. **范围蔓延**——今天加这个功能，明天加那个动画，三个月没发布
3. **异常没想清楚**——主流程跑通了，一碰边缘情况就崩
4. **没有成功标准**——做完了不知道算不算成功，不知道还做不做下去

这套工作流用**5个Phase**解决这4个问题，总耗时30-60分钟。

---

## 流程总览

```
Phase 1: 需求澄清（轻量三视角诊断）      10-15 min
    ↓
Phase 2: 问题结构化（Why + What + How）    10-15 min
    ↓
Phase 3: 概念版对齐（≤200字，≤3个功能）     5 min
    ↓
Phase 4: 范围冻结（强制确认，防止蔓延）      2 min
    ↓
Phase 5: 落地版PRD（工程精确规格）          20-30 min
    ↓
六大盲区自检（强制检查，一个都不能漏）        5 min
```

## Phase 1: 需求澄清（轻量三视角诊断）

**目标**：杀死模糊性。在写任何PRD内容之前，先确认你真正要解决的问题是什么。

**核心约束**：此阶段**禁止输出任何PRD内容、功能列表或技术方案**。只提问，只澄清。

### 第一轮：用户视角（2-3个问题）

每次只问最多2个问题，等用户回答后再继续。

必问（选最关键的2个）：
1. **目标用户是谁？** 具体一点（不是"年轻人"，而是"25-35岁刚转型自由职业的设计师"）
2. **他们现在怎么解决这个问题的？** 现有的替代方案是什么？
3. **你的产品帮TA解决的是哪"一件事"？** 只能写一件，不能写一堆。
4. **这个场景下用户会多久用一次？**（每天 / 每周 / 偶尔）——这决定了产品形态和交互深度

### 第二轮：商业视角（全部询问）

1. **这是给自己用的工具，还是要卖给别人？**
   - 如果是自用 → 简化商业部分，聚焦"解决我的什么问题"
   - 如果要卖 → 继续问定价和付费模式
2. **如果收费，模式是哪种？** 一次性买断 / 订阅 / 免费增值 / 广告？
3. **你预期把这个产品做多久？** 验证型项目（2周内出结果）/ 中期副业（3-6个月）/ 长期事业？

### 第三轮：技术视角（按需询问）

不需要全部问，根据项目复杂度选关键的：

1. **产品形态？** 微信小程序 / iOS App / Android / H5 / Web App / 浏览器插件？
2. **是否需要用户账号和登录？**
3. **数据存在哪里？** 本地存储 / 云端 / 混存？
4. **是否依赖第三方服务？**（支付、地图、AI API、短信等）
5. **这个版本预期几周内能做出来？**

---

## Phase 2: 问题结构化（Why + What + How to measure）

**目标**：用产品经理的思维框架，把Phase 1的信息组织成"可验证的假设"。

**不是让你写大文档**，而是用4个填空来强迫思考：

```
## 问题结构化

### 1. 用户与痛点（Who & What）
目标用户：[一句话具体描述]
他们现在用 [现有方案] 解决 [问题]，但遇到 [具体痛点]。
这个痛点之所以痛，是因为 [量化或质化的影响]。

### 2. 产品假设（Why this solution）
我假设做一个 [产品形态]，提供 [核心能力]，
能帮用户 [达成什么具体结果]，
比现有方案好的地方是 [差异化点]。

### 3. 成功指标（How to measure）
如果这个产品做对了，我会看到：
- 核心指标：[一个可数字化的结果，如"7日留存率>30%"或"每天自己主动用"]
- 验证标准：[什么信号出现，说明这个假设成立？]
- 失败标准：[什么信号出现，说明应该停止或转向？]

### 4. 时间盒（Timebox）
- 开发截止：[具体日期]
- 验证截止：[上线后多久做决策，如"上线2周后看留存"]
- 最大投入：[最多愿意花多少时间/钱在这个版本]
```

**关键原则**：
- 如果你写不出"失败标准"，说明你想得还不够清楚，或者这个产品不值得做。
- 如果你写不出"比现有方案好的地方"，说明你做的可能是伪需求。

---

## Phase 3: 概念版对齐（≤200字，≤3个功能）

**目标**：用极简的概念版，验证方向是否对齐。概念版必须短到可以发在微信里。

**模板**：

```markdown
## 概念版 PRD

核心用户：[一句话]
要解决的一件事：[一个具体痛点]
产品形态：[平台]
最小可用版功能（≤ 3 条）：
  1. [功能一：用户能完成什么]
  2. [功能二：用户能完成什么]
  3. [功能三：用户能完成什么]
本版本不做：[明确排除的功能，至少写2条]
商业模式：[收费方式 或 免费/自用]
技术前提：[账号体系 / 数据方案 / 第三方依赖]
```

**输出后询问用户**：
> 以上是概念版 PRD，请确认：① 方向是否对齐？② 有需要调整的地方吗？确认后进入落地版。

- 若用户有调整 → 修改概念版后重新询问，直到确认为止
- 若用户确认 → 进入 Phase 4

**为什么必须≤3个功能？**
因为OPC创业者的资源（时间、钱、精力）极其有限。3个功能已经是MVP的极限。如果你写5个，做到第3个时就会耗尽耐心，后面2个烂尾。

---

## Phase 4: 范围冻结（强制确认）

**目标**：在写详细PRD之前，用一道"确认闸门"防止后续不断改需求。

**输出以下内容，要求用户明确确认**：

```
在开始落地版之前，请确认以下内容不会再修改：

✅ 目标用户：[从概念版填入]
✅ 核心功能（≤ 3 条）：[从概念版填入]
✅ 产品形态：[从概念版填入]
✅ 本版本不做：[从概念版填入]
✅ 时间盒：[从Phase 2填入]

如果以上任何一项需要修改，我们现在返回Phase 3重新对齐。
如果确认无误，请回复"确认"，我将输出可直接用于vibe coding的落地版PRD。
```

**纪律**：
- 收到"确认"之前，绝不进入Phase 5
- 若用户说"再加一个小功能"→ 礼貌拒绝："这超出了当前范围冻结，建议放入下版本。如需调整，我们返回Phase 3。"

## 六大盲区自检清单

落地版全部输出完成后，执行以下强制检查。**任何一项未覆盖，必须补充后再输出最终版**：

- [ ] **页面结构**：是否输出了「三、页面结构与导航设计」章节？每个主要页面的职责、元素、不展示内容是否明确？独立页面/弹窗的触发条件是否说明？
- [ ] **异常交互**：每个功能的用户流程是否包含异常路径？（不能只写成功路径）
- [ ] **状态机**：所有有状态的功能，状态是否完整列出？每个状态的进入和退出条件是否明确？
- [ ] **字段规范**：每个输入字段是否有类型、必填、长度、校验规则、错误提示？
- [ ] **文案规范**：空状态、加载、成功、失败、权限、网络异常六类场景文案是否齐全？
- [ ] **流程图**：用户流程是否包含分支和异常分支？（不能是单一直线流程）

**自检通过后，输出**：
> "PRD 落地版已完成，六大盲区均已覆盖。范围已冻结（Phase 4确认），可直接用于 vibe coding。"

## 与标准PRD的区别（快速参考）

| 维度 | 传统PRD（prd-development） | prd-vibe（本Skill） |
|------|---------------------------|-------------------|
| **目标读者** | 团队（PM/设计/工程/老板） | AI编程助手 + 你自己 |
| **核心目标** | 组织对齐、范围共识 | 快速开发、防止蔓延 |
| **战略分析** | TAM/SAM/SOM、竞品分析、OKR对齐 | 简化为"产品假设 + 成功指标" |
| **用户研究** | 要求discovery数据、访谈记录 | 轻量三视角提问即可 |
| **文档长度** | 8-10章节，2-4天 | 5章节，30-60分钟 |
| **范围控制** | Out of Scope章节 | 强制冻结确认（Phase 4闸门） |
| **异常处理** | 提及风险 | 六大盲区强制覆盖 |
| **可直接coding** | ❌ 需工程师翻译 | ✅ 精确到字段、状态、文案 |

## 常见陷阱

### 陷阱1：Phase 1就开始想技术实现
**症状**：用户刚说"我想做一个记账App"，你就开始想"用SQLite还是云数据库"。
**后果**：技术方案绑定了一个未经澄清的需求，后续发现需求变了，技术债已欠下。
**修复**：Phase 1只问"用户、痛点、场景"，技术问题放到Phase 1第三轮，且只问必要的技术约束。

### 陷阱2：Phase 3的概念版超过200字
**症状**：概念版写了500字，功能列了5-6条，还加了"未来可以..."
**后果**：范围从一开始就没有控制住，后续必然蔓延。
**修复**：超过200字强制删减。如果删不掉，说明你想做的不是一个MVP，而是一个大产品——把它拆成多个MVP。

### 陷阱3：Phase 5漏掉"空状态"
**症状**：所有功能描述都只写了"有数据时怎么样"，没写"没数据时显示什么"。
**后果**：AI vibe coding时会随便生成一个"暂无数据"，用户体验差，而且往往要返工。
**修复**：六大盲区自检第5项强制检查文案规范，空状态必须写。

### 陷阱4：没有失败标准
**症状**：Phase 2的成功指标只写了"希望用户喜欢"，没写"什么情况下我会停止"。
**后果**：陷入沉没成本陷阱——明明产品没人用，还不断加功能试图"挽救"。
**修复**：Phase 2的"失败标准"必须写。这是OPC创业者最重要的纪律。

## 进阶用法

### 用法A：快速自审（5分钟）
如果你已经有一个想法，不想走完整流程，用以下清单自审：

1. 用户是谁？（越具体越好）
2. 他们现在怎么解决？
3. 我只做一件事，这件事是什么？
4. 成功的数字指标是什么？
5. 失败的标准是什么？
6. 这个版本最多3个功能，它们是？
7. 这个版本明确不做的是什么？

答完这7个问题，你已经比90%的独立开发者想得更清楚了。

### 用法B：研究型项目（需要深度调研时）
如果你的项目需要用户访谈、竞品分析、市场验证，在Phase 1之前增加一个**预研环节**：
- 用 `hv-analysis` 做竞品/行业分析
- 用你自己的社会调研方法（访谈、观察）获取一手信息
- 把预研结论作为Phase 1的输入

### 用法C：与AI协作开发
Phase 5落地版完成后，直接这样用：

```
基于以下PRD，帮我用 [技术栈] 实现。请严格按页面结构和功能说明开发，异常处理必须覆盖所有列出的场景。

[粘贴Phase 5完整内容]
```
